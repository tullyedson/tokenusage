AI Usage 0.6.1 · Routing requirements and integration contract

One model name.
Your fallback list.

Create a pool named flash-models. Add Go's GLM, a DeepSeek model from Ollama Cloud, and Qwen on local Ollama. Put them in the order you want. Other apps request flash-models; the router follows that exact list and returns to an earlier entry after its allowance resets.

Plan only is the default. There is no paid fallback option. Keep provider-side overages, extra credits and automatic top-ups disabled. The subscription APIs do not expose a verified per-request no-overage switch and the app cannot inspect or change the external billing settings.

Set it up

  1. In Settings, connect a supported subscription account or local model server. New supported accounts include their models by default. Add separate accounts with their own labels and credentials as needed.
  2. Open Models. The left side lists all discovered models by account, with search and filtering. The client API advertises those names automatically. Expand Show automatic model names to inspect or edit the default grouping of identical IDs.
  3. Enter a common model name and choose Create. Spaces become hyphens. Drag models from the left into the pool or select the pool and use Add. Drag entries to reorder them or use the arrows.
  4. Choose Save pools. Empty pools can be saved but are not advertised. Unsaved drafts survive navigation and catalog refresh. A failed save preserves the draft.
  5. On Routing, generate and save a local client key, enable the router, and copy the base URL and key to a calling app. Saved keys cannot be displayed again. The README covers connection fields, setup commands and troubleshooting.

Example behavior

flash-models
  1. Go account       -> glm-5.3-flash
  2. Ollama Cloud     -> your chosen DeepSeek model
  3. Local Ollama     -> your installed Qwen model

Use model IDs from your actual catalogs. These example choices do not install models or assume they exist on every account. The router skips disabled accounts, exhausted allowances and unavailable models. Every new request starts with entry 1, subject to known cooldowns. After a reset, it checks again rather than assuming the allowance refilled. All entries may have different IDs or belong to the same provider. Duplicate account/model pairs are rejected.

There are no separate backup-model rules or global account priorities. A custom pool overrides automatic grouping with the same name. Reset to automatic removes the custom override. Names are case-sensitive, have at most 200 ASCII characters, and accept letters, digits, dots, underscores, colons, slashes and hyphens.

Live routing reports

Open Reports to follow active requests by pool name, provider, account and actual upstream model. Cards distinguish finding a pool, waiting for an account, checking allowance, contacting a provider and streaming. Each concurrent request has its own card and a request number, also returned in the x-ai-usage-request-id response header.

The last 100 finished requests remain in memory, with elapsed time, outcome and expandable fallback steps. Steps identify skipped and selected entries, safe reasons, and retry/reset dates when known. Search by pool, provider, account or model and filter by outcome or fallback. Clear history removes only finished reports. Active requests continue unchanged. Reports refresh every second while the tab is mounted; closing the tab stops its polling.

Only valid requests admitted to the router's concurrency limit are recorded. Discovery, authentication failures, malformed inputs, disabled-router responses and busy rejections are outside these reports. No prompts, responses, tool arguments, caller session IDs, keys, URLs or raw upstream error bodies are retained. History and request numbering reset when AI Usage exits. A request keeps at most its latest 64 routing steps, with an omitted-step count.

Streaming HTTP 200 indicates an accepted connection. Completion requires a terminal marker and a clean upstream finish; a later error or truncated stream is reported as failed. Cancellation and client disconnect finalize the report. Completion does not prove client delivery or execution of returned tool calls. Reporting does not add provider requests, alter fallback order or replay interrupted output.

Calling API

Base URL: http://127.0.0.1:43129/v1. Use Authorization: Bearer <client key>. GET /v1/models discovers and lists provider model IDs and nonempty custom pools. It does not guarantee remaining allowance or support for every option. POST /v1/chat/completions accepts JSON.

{
  "model": "flash-models",
  "messages": [{ "role": "user", "content": "Explain this idea." }],
  "stream": true
}

Supported fields: model, messages, stream, stream_options, temperature, top_p, max_tokens, max_completion_tokens, stop, seed, frequency_penalty, presence_penalty, response_format, tools, tool_choice, parallel_tool_calls, logprobs, top_logprobs, reasoning_effort, and n. Only caller-executed function tools are supported. Choose pool entries that support the requested tools, context length and options. Responses, embeddings, audio, images, model installation and native agent execution are not provided.

Success responses preserve completion content and tool calls in JSON or SSE, with the requested pool name in the model field. Headers x-ai-usage-account, x-ai-usage-model, x-ai-usage-upstream-model and x-ai-usage-requested-model identify the selection. The upstream-model header contains the actual server model ID.

Clients can send x-ai-usage-session (or x-opencode-session) with a stable opaque conversation ID, 1-200 letters, digits, underscores or hyphens. Otherwise a per-request ID is generated. Only Go receives session metadata. Arbitrary caller headers and the local client key are never forwarded upstream.

OpenCode integration

Merge the provider example, save the router client key using Other with ID ai-usage, and copy the plugin into .opencode/plugins/. Restart OpenCode after saving pools. The plugin reads its ai-usage client key from OpenCode's auth file and imports all router model names on startup. It sends the key only to the IPv4 loopback router, synchronizes context/input/output limits even for existing model entries, preserves labels/options, and forwards opaque session IDs. It does not read project source or prompts.

Each name imports the chain limits returned by the router. An unknown context/output bound replaces stale values with an unverified client budget of 16,384/4,096 tokens. Input/output never exceed context. Existing explicit limits remain only when the router is offline or an older router returns no limit metadata. Replace the project plugin and restart OpenCode when upgrading; running sessions do not reload it automatically. Tool support remains assumed for the agent. Verified against OpenCode 1.18.29.

Model capacity

GET /v1/models returns limit: { context, input, output } in tokens, plus context_length and max_output_tokens aliases. Unknown values are null. A chain advertises the minimum of each field across all enabled eligible entries. Depleted members remain part of this minimum. Missing models, stale catalogs and unknown bounds are not treated as unlimited. Disabled accounts are excluded until re-enabled. Models displays provider and chain limits, including unsaved pool edits.

GLM-5.3-Flash on Go and Ollama Cloud advertises 1,000,000 context tokens. A smaller-context local fallback lowers that chain's limit. Go uses exact provider/model limits from OpenCode's public Models.dev catalog. Cloud Ollama adds native /api/show context metadata. vLLM uses its served max_model_len, local Ollama uses explicit model num_ctx bounded by the trained maximum, and OpenRouter uses its eligible catalog bounds. No model-name heuristics are used.

The public supplement is credential-free, bounded to 16 MiB and cached for five minutes; expired limits are discarded after a failed refresh. Optional Ollama metadata enrichment has a four-second overall budget and eight parallel reads. Model discovery still returns names when optional metadata is unavailable. Generation preflight does not fetch the public supplement. The provider counts tokens and enforces its capacity. The router does not trim history; JSON requests have a separate 16 MiB transport limit.

Selection and lifecycle

  • A pool's account/model sequence defines order. A later exact-name match never jumps ahead of an earlier different model. Automatic groups use stable account-ID order until customized.
  • Catalogs are cached for five minutes, failed reads retry after 30 seconds, and Refresh models forces a read. Failed catalogs retain names with an error only while account configuration is unchanged. Catalog reads never generate text.
  • Requests serialize per account, including streaming. Queued work rechecks cooldowns after acquiring an account. The router allows eight active requests.
  • Known quota failures supply reset/retry time and model/account scope. HTTP 429 is treated conservatively as account-wide. Retry-After is honored, otherwise retry is after 60 seconds. Cooldowns are held in memory and reset permits a new provider check.
  • Connection refusal and HTTP 401/403, 402, 404, 429 or 503 may try the next entry before output. Other errors and ambiguous submissions stop. Interrupted streams are never replayed elsewhere.
  • Saving accounts, pools or routing cancels active requests, including streams whose caller stopped reading. Disabling an account prevents new requests. Disabling the router releases its port. Exit ends the app and listener.
  • Requests and streams have bounded waits. Requests are limited to 16 MiB, JSON replies to 8 MiB, and each SSE event to 1 MiB. A bounded channel limits buffered streaming data. The app does not log or persist prompts or responses.

Provider extension boundary

IUsageProvider::inference() optionally returns IInferenceProvider. Implement definition, validate, models and prepare. The models method returns Vec<InferenceModel> with exact IDs and optional ModelLimits context/input/output token counts. Metadata drives Settings, discovered names populate Models and the client catalog, and prepare checks availability and constructs a fixed safe upstream request. Exhaustion returns Unavailable with retry time and scope. Every applicable allowance must permit the request.

The engine owns pool order, catalogs, concurrency, credential isolation, transport, streaming and cancellation. Adapters must not use consumer subscription meters to authorize unrelated paid keys. Go and Ollama depend on the provider-side billing prerequisites above, which the available APIs cannot inspect or change. There is no paid fallback option. Extend protocols behind this interface with HTTP fixture tests, without provider-ID branches in core or HTML. See Adding providers.

Storage and migration

Version 1 and 2 settings load as version 3. Legacy aliases, global priority and breadth-first fallback rules flatten into explicit pools in their effective order. Enabled/excluded flags, account IDs, Windows Credential Manager targets and browser profile generations are preserved. Loading does not overwrite the original file; the next successful settings save writes version 3.

ModelPool has a name and an ordered array of PoolMember accountId/model pairs. Only custom pools are persisted; catalogs and automatic groups are held in memory. Router connection saves preserve pools. New account IDs are random and stable. Keys live in Windows Credential Manager and never return in bootstrap data. Forget clears only the selected account's keys and sessions.

The API binds IPv4 loopback, requires authentication, and rejects browser Origin headers and unexpected Host values. Local URLs allow loopback/private IPs without credentials or arbitrary paths. Redirects and system proxies are disabled. Remote sign-in windows have no app-command permissions.
